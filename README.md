# Inkling

Go coding agent for `thinkingmachines/inkling-small` through OpenRouter. Standard library only; macOS and Linux.

## Install

```sh
curl -fsSL https://raw.githubusercontent.com/dylantirandaz/inklingharness/main/install.sh | sh
think login
think
```

OpenRouter credits are required. Prompts and tool results go to the provider; do not send private code without checking its data policy.

## Use

```sh
think run "Find and fix the failing test"
think chat -resume last
think run -h
```

Includes file tools, Bash, saved chat, JSON events, RPC, and ACP.

File changes, commands, and web requests require approval. `-yes` disables it. Commands are not sandboxed. `OPENROUTER_API_KEY` overrides the stored key.

`web_search` sends queries to [Exa's free, rate-limited service](https://exa.ai/docs/get-started/exa-mcp); no extra key is required. `web_fetch` reads source URLs. `-no-web` offers neither tool and leaves them out of the built-in prompt, for example when a benchmark must not look up answers.

`think run -lean` is a headless profile for Inkling Small. It adds `read_files`, which reads up to 8 files or line ranges in one call, because the model makes one tool call in a message. It keeps less of a large result in the conversation: `read_file` returns 400 lines by default instead of 2,000, and bash keeps 8 KiB of a large output instead of 32 KiB (the full output stays in a file). It leaves out `task`, `remember`, `inspect_images`, and `context_checkpoint`, and the lines of the prompt about them and about parallel calls. Do not use it for images. Without `-lean`, the request is the same as before.

In `-lean`, a `read_file` or `read_files` call that has the same input as an earlier call in the same run, and gets the same result, gets a short note that names the earlier call. The model has that result in its context already. A file that changed gets its full content. If the model asks a third time, it gets the full content again. Compaction removes the earlier results, so after it each read is full again. On the 232 recorded Think trials of SWE-bench, this changes 126 of 8,815 tool results and removes 3.5% of the tool-result characters. Measure it again with `THINK_REPLAY_EVENTS='/full/path/out/terminal-bench/jobs/swe-bench-more-*/*/agent/think-events.jsonl' go test ./internal/agent -run TestReplayRepeatedReads -v`; the test calls no model.

Chat opens with the artwork of the [Inkling page](https://thinkingmachines.ai/inkling/): an ink blot with three colored shapes. The page draws it from a seed. Chat picks one of the page's seeds from your project path, so each project keeps its own picture. The picture needs 256 colors, 64 columns, and 24 rows. A smaller terminal shows the project name only. The shapes match the page for each seed.

Chat follows the rules that make Claude Code and omp look sharp: normal case, one glyph for each kind of thing, and no ornament. Its art comes from the Inkling page, and every color means something: the blue, red, and green of the picture's three shapes, and the plum-to-blue of the page.

- The opening is the artwork of the page. It soaks in for one second, wet ink bleeding at its edges, and dries to flat, crisp shapes. The project name and the model hang under it.
- Your prompt sits on a faint band across the row with an edge of blue ink, in bold, with the time at its right end.
- A tool is an ink drop and a row that reads as one sentence, `● Read app.py · 9 lines  #1`, with what it left behind hooked under it by `⎿`. The drop tells what the tool did: blue for a read or a search, green for a change, ink for a command, and red for a failure. The time shows only for a step of a second or more, a failed command names its exit code in the row, and the tab number for `/tools` is faint. A diff is a block of red and green tints with line numbers, and every line of the block has the same width, so the tints form clean rectangles.
- Every box is rounded. A box that waits for you has an edge that fades from plum to blue; a box that you only read, such as `/status` or `/context`, has a gray edge.
- An approval is such a box: the action in bold, the whole change or command, and what the action can touch. Under the box is `❯ Allow?   y once   a this session   n no`. Enter and Esc deny. Nothing moves while a request waits.
- The composer is the same box, one row tall until your text needs more, with a `❯` in the model color. The command menu and `/help` use the same `❯` and colors.
- While the model works, the working row is the next step that has not landed: a drop in the model color forms and falls in the column of the step drops, then the status and the seconds. The right end of the row is a ticker tape: a head moves at a steady pace, and each tenth of a second in which a piece of the stream arrived leaves a fine tick, so the rhythm of the model is the pattern. A finished step leaves a taller tick in the color of its drop.
- A streaming line shows without its Markdown marks, so a `**` or a backtick never flashes before it turns into style.
- A finished turn is signed with its score: one drop for each step, in order and in the color of what the step did, then the wall time, the requests, and the tokens in gray. So the scrollback keeps the shape of every turn: `●●●●●` is two reads, a change, a failure, and a command. A row of air follows it.
- A turn that fails shows a red bullet, `● Turn failed` (or `● Turn stopped`), with the cause hooked under it: for an HTTP error, its status and the provider's message, not the raw body; for a network error, the host that could not be found or reached, and why.
- Labels name files from the project, so a step reads `Read app.py`, not the full path. The work of an approval keeps its paths exactly as the model wrote them, because you approve what will run.
- A code block shows its language in gray above the code and ends in air. In `/tools`, each tab opens with the drop of its step, and a change shows its red and green lines.

A frame of the tape costs about 1.1 µs and one allocation. Every color is flat except the box edges, which fade in twelve steps, so chat writes few bytes to the terminal: about 17 KB a second while the model streams, and nothing while an approval waits. `INKLING_MOTION=off` keeps every row still. A terminal with fewer than 256 colors keeps the plain look: a rail for each tool with the same drops, a marked row for each prompt, and one amber box for an approval.

Most of the wait in a chat is the model, not Think. On October 21 a one-word reply took 2.07 s, of which Think used about 1 ms; the rest was the network (42 ms) and the provider (0.3 s to the response headers and 1.3 s more to the first token, after a long idle). In a chat that had started fresh, the first token of "hi" came after 0.45 to 0.6 s. A request that warmed the provider's prompt cache at start did not help: the tools, which come first in every request, are cached already, and with the warm request the first token came after 0.85 to 1.5 s (3 runs each), so chat does not send one. The speed of a turn is set by the reasoning: Inkling Small reasons at high effort by default, and `-effort medium` answers a task in about a sixth of the time and cost, with lower success on hard tasks (see the effort table below).

Chat keeps normal terminal scrollback and a fixed multiline composer in a rounded box. Ctrl-J adds a line. Up/Down moves within a draft; Ctrl-P/Ctrl-N selects history. Paste stays editable. Each prompt you send stays on its band, with the time at its right edge.

You can type while Inkling works. Enter queues a steering message: it goes to the model with the next tool results, or, if the model has already answered, the model answers again with it. Alt+Enter queues a message for later, which starts the next turn when the current one ends; a `/command` always waits for later. Queued messages show above the composer. Alt+Up moves them back into the composer, and a stopped or failed turn does the same. Each steering message shows as a sent prompt where it took effect. An approval ignores keys for 0.4 s after it appears, so a key typed for the draft cannot answer it.

A reply is plain text with one left margin: no marker, inline code and file paths in azure, and bullets in the model color.

The footer has two rows under the composer. The first row names the folder and the Git branch at the left, and the model and effort at the right. The second row has the keys at the left, and the context gauge and the session tokens at the right. A terminal shorter than 16 rows keeps one row.

Type `/` to open the command menu. Up/Down selects a command, Tab completes it, and Escape closes the menu. Enter runs a command without arguments. For a partial command that takes arguments, Enter completes the name and leaves the input open. An exact command name runs on Enter. Project commands also appear in this menu. On terminals smaller than 20 columns or 8 rows, type commands directly.

Tool numbers continue across model requests for one prompt. `/tools` opens the saved tool results for the last prompt; `/tools N` selects a tab. `/diff` shows current Git changes against HEAD, one file per tab with its added and removed line counts, including new non-ignored files, without changing the index.

Detail views use a separate screen buffer only while open. The tab row names each document; a rule and a scrollbar frame the text on screens at least 40 columns wide. Up/Down or j/k scrolls; PageUp/PageDown moves a page; Home/End or g/G moves to the start or end. Left/Right, Tab, or a digit selects a tab. Escape, q, Enter, or Ctrl-C returns to chat. These views do not animate while idle.

The context gauge is four cells against the compaction threshold, and the session tokens include cache tokens. The context count updates after each model request. `/help` lists the commands and keys in two tables; `/usage` shows token counts.

`/status` and `/context` show rounded gray cards. Each card has a waffle of squares: `/status` shows the context against the compaction threshold, and `/context` gives each kind of content its own color.

Use `think chat -show-thinking` to show reasoning. The Go renderer batches partial reasoning on its 33 ms frame timer, including when animations are off. Complete lines and text at reply, tool, status, or finish boundaries print at once.

## Context and images

Attach with `-file path` or `@path`. An `@path` attaches a file only when that regular file exists; any other `@word` stays in the text, so pasted issue text cannot stop a run. Images stay in private session state: 5 MiB each. `inspect_images` sends up to eight images (10 MiB total) per request. Later turns reuse notes; re-inspection uses the original even after source deletion.

Use `context_checkpoint` for working notes and `context_read` for exact older messages. Notes are lossy, not a privacy filter. Back up the session `resources` directory; chat exports exclude resources.

Summary requests disable tool calls.

## Evaluate

Tasks for `think eval`: `evals/tasks.jsonl` and `evals/harder.jsonl`. Replies do not prove success.

Terminal-Bench 2.0 supports seven native harnesses on 89 tasks in VMs, including OpenCode and Goose. Install `harbor[modal]==0.24.0` and `modal==1.6.1`, configure Modal authentication, and set `OPENROUTER_API_KEY`. From the repository root:

```sh
mkdir -p out/terminal-bench &&
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -ldflags '-s -w' -o out/terminal-bench/think-linux-amd64 ./cmd/think &&
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -ldflags '-s -w' -o out/terminal-bench/harbor-wire-linux-amd64 ./evals/harbor-wire &&
python -m evals.harbor_run evals/terminal-bench.json &&
python -m evals.harbor_wire out/terminal-bench/jobs/terminal-bench-2.0-native
```

`compact_tokens` sets Think's threshold. Native launches use scripts. Verify Messages/Responses routes. Seven-harness results show no universal lead.

The no-harness arm is `evals/bare`: the model, one bash tool, and a loop. It sends no system prompt and does no planning, context management, or recovery. The loop ends when the model answers without a tool call. `evals/terminal-bench-no-harness.json` runs it next to Think on the same 89 tasks, in the same VMs, with the same recorder profile. Build `bare-linux-amd64` as you build Think, then run `python -m evals.harbor_run evals/terminal-bench-no-harness.json`.

`python -m evals.compare_arms --output FILE --arm LABEL=SOURCE:HARNESS ...` builds one table from several arms. SOURCE is a Harbor job directory or a saved outcomes file. A label can repeat: sources with different tasks add tasks, and sources with the same tasks add attempts. The table has the pass rate with its 95% interval, which resamples tasks because the attempts at one task are not independent. It also has ungraded trials, errors, cost per trial and per pass, tokens, agent time per trial and per pass, and install time. The first arm is the reference of the paired comparisons, which use an exact sign-flip test on the number of attempts that each arm passed at each task. A second table compares cost and time on the tasks that both arms passed, as a ratio with a 95% interval, so an arm cannot look cheap by quitting early. `--drop-ungraded-tasks` removes each task that has an ungraded trial in any arm, from every arm.

Result on Inkling Small, one attempt for each of the 89 tasks: no harness passed 49 and Think (commit 3a76490) passed 48. These two ran in one job on October 18. Pi 0.87.1, Claude Code 2.1.205, and Codex 0.146.0 passed 38, 41, and 26 in the October 10 run, which used Harbor 0.21.0. The 95% intervals of no harness, Think, Pi, and Claude Code overlap. Only the gap between Think and Codex is clear (exact paired test, p < 0.001). Think and no harness differ by one task, so they are tied. The task environments were open to the internet in these runs too; see the audit below.

The native-setup comparison asks two questions: does Think help Inkling Small more than other harnesses do, and how much less does it cost? It runs Think, Claude Code 2.1.205, Codex 0.146.0, Pi 0.87.1, and the no-harness baseline on the 89 Terminal-Bench 2.0 tasks and on 40 SWE-bench Verified tasks, drawn with seed 20261018. Each harness has one attempt at each task. Harbor installs Claude Code, Codex, and Pi with its own agents. `evals/harbor_think.py` and `evals/harbor_bare_native.py` add Think and the baseline the same way: each uploads a Linux build and runs it once for each task. The baseline also uploads a CA bundle, because some task images have none and a static Go binary reads only the system bundle. All five use `thinkingmachines/inkling-small`, high effort, and one OpenRouter key. OpenRouter lists one provider for this model, DeepInfra.

No recorder sits between a harness and the provider, so each harness keeps its own prompts, tools, turn limits, and output limits. Token counts are the counts that each harness reports. `out/terminal-bench/native-run-identity.json` names the digest of each Think and baseline build, and the patch over commit bb81b1e that builds them. Do not change a job's config after it starts. Harbor resumes a job only when its config is the same: run the same command again, and it keeps finished trials and removes unfinished ones, so copy those first.

Run each job with `python -m evals.budget_guard --backend modal --limit DOLLARS --min-credits 6 --job-dir JOB_DIRECTORY PID_FILE`. When the guard stops a job, the agents inside its Modal sandboxes keep running and keep spending credit. The guard therefore terminates the sandboxes of the job's trials, and only those, and fails if any remain after 120 seconds. Keep the credit floor well above the cost of the requests in flight: with about 40 concurrent trials, OpenRouter answered 402 to new requests at about $3.50 of credit, and those requests ended trials with an error. Remove such trials before you resume, whatever their grade.

The first native runs, on October 18, had open task environments, and agents used the internet to fetch the answer. On SWE-bench, 37 of 280 trials retrieved most of the reference patch from GitHub: Think in 25 of 71 trials, Claude Code in 8 of 69, Pi in 2 of 70, and Codex in 2 of 70. 36 of those 37 trials passed. Think has web search and fetch tools, and Claude Code has WebFetch. Pi and Codex used `curl`. On Terminal-Bench, 7 of 491 trials fetched a reference solution from the benchmark repository: Think in 5, Claude Code in 1, and Codex in 1. In two Codex trials on one task, the model wrote the full hash of the upstream fix commit without having seen it. Those runs did not log the commands of the baseline, so its trials could not be audited.

The clean run closed this on SWE-bench. `evals/closed_tasks.py` wrote local copies of the 40 tasks, and in each copy the agent phase can reach only `openrouter.ai`. The setup phase stays public, so each harness still installs itself. A probe agent confirmed this in the real phases: `openrouter.ai` answered, and every other host and raw IP address was reset at once. The tool also put the `testbed` conda environment first on the PATH of each image. Without it, a plain `bash -c` gets the base Python, which lacks the dependencies of the repository, and Codex, which starts `bash -lc`, would have had the right Python alone. Every harness had its web tools off: `-no-web` for Think, and `disable_web_search` for Claude Code and Codex. Pi and the baseline have none. The build of the baseline logs each command and its output. `evals/swe-bench-closed.json` runs all five on the 40 tasks. Terminal-Bench kept its open network in that run, and an audit checked it instead. The airgapped run below closes both benchmarks.

Before the airgapped runs, the clean SWE-bench run gave one attempt at each of 40 tasks. It is the first attempt of the SWE-bench results below. Think passed 31, Pi 30, Codex 29, Claude Code 27, and the baseline 26. The audit found no lookup in any of the 200 trials. The agents still tried: in 26 trials an agent ran a network command, and every attempt failed. Closing the network moved each harness by -2 to +3 tasks, and the five harnesses together from 149 to 143. 14 tasks had a trial that retrieved the fix in the open runs. 11 of them are still solved by at least 3 of the 5 harnesses. Only `django__django-13195` is solved by none.

A model can still know an answer from its training data. One Codex trial recalled the hash of a fix commit, and a cold probe that asked for fix hashes got UNKNOWN for 39 of 40 tasks. Use tasks that are newer than the model if you can. The intervals are wide because each benchmark has few tasks.

The API key is another path out of a closed network. The key is in the environment of every agent, and `openrouter.ai` is the one host that stays open. An agent can call any model with it, and some models search the web. The airgapped runs used a key that is not confined: it can use 467 other models, so `evals.preflight` fails. The decision for these runs was to keep this key, so they do not use `--require-confined-key`, and the audit is the control. The audit found 3 of 530 Terminal-Bench trials that used the key, and none in 580 SWE-bench trials (details below). To remove the path, use a key that a guardrail confines to `thinkingmachines/inkling-small`: in the OpenRouter dashboard, create a guardrail with that model as its only allowed model and a daily budget, create a key for the benchmark, and assign the guardrail to the key. Store the key in `~/.config/inkling/benchmark-key`, where `out/terminal-bench/with_key.py` reads it first, so your Think login does not change. Then run `python out/terminal-bench/with_key.py evals.preflight`. It fails unless the key lists exactly one model. A guardrail cannot block the web search of OpenRouter on the allowed model, so the audit stays necessary.

The airgapped run does not use tasks that need the network. Many reference solutions download things, so a task is in the airgapped set only if its reference solution passes with the open network and in two runs with the agent phase closed. `evals/oracle-open-terminal-bench.json`, `evals/oracle-closed-terminal-bench.json`, and `evals/oracle-closed-terminal-bench-2.json` run the reference solutions. 53 of the 89 Terminal-Bench tasks qualify. 22 need the network, 13 fail everywhere, and one has an inconsistent result. Of the 40 SWE-bench tasks, 38 qualify. `psf__requests-2317` is out because the base conda environment of its image holds `requests` 2.31.0, which contains the fix and which conda needs, so it cannot be removed. `pylint-dev__pylint-7080` is out because its reference patch fails 3 of its own tests in this environment, and no harness passed it in 11 attempts. `evals/airgap-tasks.json` lists every task and the reason. `python -m evals.closed_tasks --layout git --source ~/.cache/harbor/tasks --dest out/terminal-bench/tb-closed --allow-host openrouter.ai` closes the Terminal-Bench copies. `python -m evals.closed_tasks --layout packages --swe-image --source ~/.cache/harbor/tasks/packages/swe-bench --config evals/swe-bench-airgap-1.json --dest out/terminal-bench/swe-bench-airgap --allow-host openrouter.ai` closes the SWE-bench copies. `--swe-image` also deletes the conda and pip caches, because the conda cache of an xarray image holds xarray 2025.4.0, which contains the fix of two tasks.

A probe agent, which calls no model, checked the closed copies of all 129 tasks in the real phases. The agent phase reached `openrouter.ai`, and nothing else: HTTPS to GitHub, PyPI, and a neutral site, TLS to the IP address of GitHub, plain HTTP, SSH, and `curl` all failed. A TLS connection to the IP address of GitHub with the name `openrouter.ai` reached the edge of OpenRouter, which answered 403, because the filter follows the name. DNS lookups still resolve. The probe also found no copy of a reference solution or a test file outside the files that the task provides, no test folder, and no commit outside the history of HEAD, except the v3.5.1 tag of `matplotlib__matplotlib-22719`, which is older than the issue and does not hold the fix. The HEAD of a SWE-bench repository is a synthetic commit dated 2026, so a check that asks for a commit newer than HEAD cannot fail; ask for commits that are reachable from a ref but are not ancestors of HEAD.

`python -m evals.audit_trials --output audit.json JOB_DIRECTORY ...` reads what each agent ran and marks a trial invalid if the agent called the model API from its shell (the host, a key, or a base URL variable), called a web tool, or received the reference patch or a benchmark solution. It notes trials that tried a network command or searched for credentials. `python -m evals.compare_arms --audit audit.json ...` counts an invalid trial as not passed, so cheating gains nothing. On the open runs the audit reproduces the earlier counts and also finds web tools in 16 of 40 Think trials and 10 of 40 Claude Code trials on SWE-bench; on the closed SWE-bench run it finds no invalid trial among 200.

Cost and time, on the tasks that two harnesses both passed (both benchmarks pooled): Think used 0.45 times the money of Claude Code (95% interval 0.40 to 0.51) and 0.54 times that of Codex (0.47 to 0.61). Against Pi (0.88, 0.79 to 0.99) the difference is small, and against the baseline (0.99, 0.88 to 1.13) there is none. What the audit and the checks found. Network: no agent got anything from outside. Of 581 steps that looked like network commands, 16 returned a download or a page without a failure. 15 of them belong to `git-multibranch`, which runs nginx and a git server on localhost. The other one is a model API call (below). Key: the audit marked 3 of 1,110 trials as invalid. In `code-from-image`, Pi asked `openai/gpt-4o-mini` to describe the image, and the trial passed; that pass is not counted. In `extract-moves-from-video`, the baseline called `claude-opus-4.8`, `gemini-2.5-flash`, `claude-sonnet-5.5`, and `perplexity/sonar-pro`, which searches the web, and used it to read a speedrun guide and the task description. In the same task, Claude Code asked `claude-3.5-sonnet` for the answer, and the call failed with a 401, because its tool shell had no key. Both of these trials failed the task. So the audit changed one result. It also shows what the unconfined key allows: one open host is a gateway to other models and to the web. One Claude Code trial that timed out wrote no agent files, so it could not be audited, and it failed. Nine trials ended with an error that is not a timeout. Codex got HTTP 422 from the provider on the image tasks `code-from-image` (2 of 2 attempts), `video-processing` (2 of 2), and `path-tracing` (1 of 2), and Claude Code got a 422 on `code-from-image` once. These count as failures. No harness passed `video-processing` or `path-tracing`, and only Pi passed `code-from-image`, so the errors cost at most 3 passes.

One integration bug changed two trials. The instruction of `pytorch-model-recovery` starts with "- ", and Harbor gives the instruction to Pi as a bare argument, which Pi reads as an unknown option. In both attempts, Pi exited in 0.7 seconds without a model call. Those two trials are not measurements of Pi, so they are archived in `out/terminal-bench/archive/pi-never-started/`, and the two trials were run again with `evals/harbor_pi.py`, which puts `--` before the instruction. The change affects no other instruction. Both new trials passed. A scan of all 1,110 trials of these runs found no other trial in which the agent did not run.

Limits. The tasks are those whose reference solution works without the network: 53 of 89 on Terminal-Bench and 38 of 40 on SWE-bench. The results do not cover tasks that need the network. Differences of a few points are not visible at this size. The baseline is not a harness-free run: its one tool is the bash tool of Think without background mode, and it echoes the reasoning of the model back unchanged. The key was not confined. Codex and Claude Code sometimes failed on images, because the provider rejected their request format.

`python -m evals.harness_tax` computes the measures of the HarnessTax study of Arena (September 2026, `arena.ai/blog/coding-agents-harness-tax`) from job folders. For each harness it gives the success rate and the cost of an attempt, averaged over the attempts at a task and then over tasks, with 95% intervals from 10,000 task resamples. It gives the Pareto frontier, and the share of resamples in which each harness is on it. It gives cost ratios, the effect of a harness on success (its rate minus the mean rate of all harnesses), model calls per attempt, and the cost of one call. It gives the cumulative cost-success curves, against cost, against turns, and against tokens: the attempts sort from the cheapest, and the curve shows the success rate that a spend per attempt buys. It gives the first model call. `--context out/terminal-bench/first-call-context.json` adds the tools, the tool-schema characters, and the instruction characters of the first request, where instructions are every text but the task prompt. I captured those with a local server that logs each request body and answers with an error, so no model was called. Think and the baseline ran from the same source as the airgap binaries, and the Linux builds are byte-identical to them. Why Claude Code is lower. The gap to Think over the 452 trials of each harness is 5.8 points (286 passes against 312). Two things explain part of it, and the rest is not clear. First, some Claude Code runs end without an attempt. On SWE-bench, 19 of 346 Claude Code trials made no edit, against 2 of 346 for Think. In 14 of them the run ended after a median of 3.5 model replies, because the reply came back as plain text that holds a tool call, for example `{"name":"Read","args":{"file_path":"...","limit":120,"pages":"}}Bash{"...}}`, and not as a tool call. Claude Code takes a reply with no tool call for the final answer and stops. In the other 5 the agent answered a question in prose and edited no file. All five harnesses fail those three tasks in every attempt, so these 5 trials do not add to the gap. With Terminal-Bench, 16 Claude Code trials ended on such text (15 on a Read call, 1 on a Write call) and 1 of them passed. Think and the baseline have no such trial in 452 each. Pi has 5 and Codex 2, all in the middle of a long file write or edit. If the 15 Read trials had passed as often as Think does on the same tasks, Claude Code would have about 11 more passes, and the gap would be 3.3 points.

The cause is the `pages` field of the Read tool of Claude Code, which is meant for PDF files. The model fills it in 619 of the 805 Read calls of these runs, including for source files, and in about 3% of the calls that have it the output breaks inside the field. 18 of the 21 garbled texts of the runs start with a Read call, and all 44 garbled replies of the replays below do. The replays use the real context of 5 trials that had failed this way: the real task prompt, the real first reply, and the real first tool result, sent to the same OpenRouter endpoint with streaming, as Claude Code does. They were about 1,770 requests and cost about $6. The unchanged request returned the garbled text in 22 of 680 replies (3.2%), and the request with `pages` removed from the Read schema in 0 of 200 (Fisher exact test p = 0.007 against the 680, and p = 0.03 against the 6 of 200 of the control of the same batch). Four other explanations changed nothing. Removing the sentence "Independent tool calls can run in parallel in one response" from the system prompt gave 5 of 240, against 7 of 240 for the unchanged request in the same batch, and replacing it with "Make exactly one tool call per response" gave 5 of 240. Removing the thinking block from the history gave 6 of 200 against 6 of 200, and cutting the 22 tools to 4 gave 6 of 200 against 6 of 200. The parallel-call sentence was the explanation that I expected from the logs, and the test showed it was wrong. The replay contexts were chosen because the failure had happened in them, so its rate is higher than the rate of the runs. The result says that `pages` is the trigger in these contexts, not that no other trigger exists. The scripts and the replies are in `out/terminal-bench/analysis-20261018/` (`replay_capture.py`, `replay_run.py`, `replay_chat.py`, `replay-results/`).

Claude Code breaks tests that passed before in more trials (30, against 13 to 18 for the other harnesses) and has fewer plain wrong fixes, but on 9 of the 23 tasks where it did so, no other harness did, and these numbers are too small to say why. These explanations were checked and do not fit. It runs fewer tests (a test command in 57% of its SWE-bench trials, 93% for Think), but running a test after the last edit is not linked to passing in these data (74.6% with it, 74.0% without, over all five harnesses). Its edits are not larger (median 341 characters of new text, against 553 for Think). No run had a context compaction, and no command timed out. On Terminal-Bench the gap is 5 trials of 106 (46 against 51), and only 1 trial ended on garbled text.

Limits of the pooled comparison. The 232 new tasks are all SWE-bench Verified with one attempt, so the Terminal-Bench part of the 323 tasks is still the 53 tasks of the earlier runs, and the pooled rates are mostly SWE-bench rates. The new tasks are harder than the first 38: Think passed 74% of them and 79% of the first 38. With 12% of the tasks discordant between two harnesses, a paired test with 80% power at p = 0.05 needs about 375 tasks for a gap of 5 points, about 1,050 for 3 points, and about 2,350 for 2 points (`python -m evals.power_analysis`). So the 232 tasks of round 1 can find a gap of about 6 to 8 points, and the small gaps stay open. An earlier version of this paragraph gave 730 to 1,200 tasks for a gap of 2 points. That was the number of tasks for an interval of plus or minus 2 points, and not the number for a test. The key was not confined, and the audit is the control.

Effort and the architecture of Inkling Small (October 20, dev tasks). The sourced notes on the model are in `docs/inkling-architecture.md`. The facts that matter for a harness are these: the model is a sparse mixture of experts (276B parameters, 12B active) with 35 sliding-window layers of 512 tokens and 7 global layers; its reasoning effort is a number that the template writes into a system message ("Thinking effort level: 0.9"), so effort is soft conditioning and not a limit; it was trained across many harnesses with random tool sets, and one tool call in a message; and OpenRouter lists no parallel tool call setting for it. On our runs, Think sent 12,563 tool calls in 12,563 turns, so the model never made two calls in one turn, although the built-in prompt asks for parallel calls.

Effort is the compute dial of the model, and it is strongly nonlinear. The same Think build and prompt, one attempt on each of the 232 tasks of round 1 (these tasks are dev tasks for any later change):

| effort | passed | dollars a trial | turns | agent seconds | dollars per solved task |
|---|---|---|---|---|---|
| low | 89 (38.4%) | 0.0038 | 7.7 | 11 | 0.0098 |
| medium | 131 (56.5%) | 0.0083 | 11.6 | 18 | 0.0146 |
| high | 171 (73.7%) | 0.0684 | 39.0 | 123 | 0.0927 |
| max | not measured on all tasks | at least 4 times high | 92 | 396 | |

A pilot at `max` was stopped by the guard at its $14 limit after 35 of 120 trials. On those 35 tasks, `max` cost $0.296 a trial against $0.074 at `high` (4.0 times), used 92 turns against 40, and passed 26 against 27. The 20 trials in flight were killed, and they were the slow ones, so the true ratio is higher and the success is not known on them; the pilot spent about $15 of credit. The effort changes what the model does, not only how long it reasons. Per trial, `low` made 4.5 reading calls, 0.4 runs of Python, 0.2 runs of tests, and 1.5 edits, and it reproduced the problem before the first edit in 14 of 232 trials. `high` made 22.7 reading calls, 7.2 runs of Python, 3.7 runs of tests, and 2.4 edits, and it reproduced first in 133 of 232. So the extra effort buys investigation and verification. Cost per solved task is 9 times lower at `low` and 6 times lower at `medium` than at `high`, and `high` is the setting for success. A cheap run rarely solves what `high` fails (4 tasks for `low`, 7 for `medium`, of 61 that `high` fails).

A cascade that tries a cheap effort first and then `high` needs a signal that the cheap answer is right, and the data have none. A cheap run almost never runs a test (221 of 232 `low` trials and 209 of 232 `medium` trials never ran a test command). At `high`, 136 trials ended with a passing last test, and 76% of them are correct, against 74% of all trials. The wrong fixes (66 of the 85 failures of Think at `high`) come from reading the request wrongly, and the model's own tests pass anyway. They also write more: on the tasks that `high` failed, the median new text was 792 characters and 2 edit calls, against 420 and 1 on the tasks that it passed (this is correlation, since hard tasks need more code).

Prompt changes did not move the result at `medium`, which was screened with a rule written before the run (`PROTOCOL.md`, section 6b). The control is the built-in prompt: 131 of 232 at $0.0083. A five-step workflow (read, reproduce, change the cause, run the reproduction and the nearest tests, read the report again) solved 129 (net -2 tasks, p = 0.86) at $0.0096, and the same workflow with a rule to make the smallest change solved 134 (net +3, p = 0.74) at $0.0098. The rule asked for 14 more tasks, so both variants are rejected, and the turns rose only from 11.6 to 12.9. The model at a given effort ignores an instruction to work more thoroughly; effort decides that. The baseline (one bash tool, no prompt) at `medium` solved 123 at $0.0090, so the harness adds 8 tasks (3.4 points, p = 0.26) at a lower cost at that effort. One trial of each of the baseline and of the first variant on `sympy__sympy-22080` met a stall of about 25 minutes between the agent and the verifier, at the time when Modal lost connections. The baseline trial ended on a verifier timeout and the variant trial has no agent log. Both count as not passed, and the cost of the second is left out.

Cost structure of Think at `high` (346 trials of SWE-bench): 77% of the dollars go to cached input that every turn reads again, 12% to uncached input, and 11% to output. The tools and the prompt that Think adds over the baseline are about 1,390 tokens in each request, 8% of the cost. The reasoning of earlier turns that later turns read back is about 14.5% of the cost. Dropping it in every turn does not pay: the message that loses its reasoning changes the cached prefix, so each turn would read about 400 more tokens at the uncached price, and the net saving is about 6% with an unknown effect on quality. A turn cap does not pay either: a cap at 60 turns would save 4.7% of the cost and lose 5.7% of the passes. The context of Think never passed 54,000 tokens (the 99th percentile is 43,000), so the compaction at 200,000 tokens and the checkpoint tools were never used, and the limits of the long context do not apply to these tasks.

The lean profile (`think run -lean`, described above) is built from these findings. It goes at the turns and at the old tool output that every turn reads again: 43.5% of the turns of Think were a read that followed a read, and old tool output was 70% of the cached input (results over 8,000 characters were 22% of it). Its first request is about 1,740 characters shorter than the default one. Without `-lean`, the new build sends the same request bytes as the frozen build. The Go tests cover `read_files` and the output limit, and the binary ran `read_files` end to end against a local server. It has not run on the model yet: the screen (`PROTOCOL.md`, section 6b, with its rule written before the run) needs about $8, and the credit of the account was $0.30 when the build was ready. The frozen build at `high` stays the build of record. The two prompt variants are rejected, `max` is not worth its cost, and the other open candidates are listed in `PROTOCOL.md`. Two incidents of this round are fixed. The cache check of the guard was set on trials of 30 to 40 turns, and it stopped the `low` and `medium` runs on a healthy provider, where the cache share is 89% and 91% (the help text of `--min-cache-hit` now says so). And a lost connection to Modal ended the guard with an unhandled error (`grpclib` raises its own classes) while three jobs went on for an hour with no limit, and they spent $12 against a limit of $9; the listing of sandboxes now treats the error as a failed read, retries it, and stops the jobs when it keeps failing (`evals/test_budget_guard.py`).

The credit is not used only by the benchmark key. After the three jobs ended, the credit of the account fell from $5.20 to $4.08 in four and a half minutes while the key of the benchmark had spent nothing (its limit left stayed at $211.88) and no job ran. Something else on the same OpenRouter account spends about $0.24 a minute, and the likely cause is the assistant that wrote these runs, whose own model calls use the account. This is inferred and not confirmed. It explains a fall of $27 that the experiments of that period do not account for, and it means that the credit floor of the guard (`--min-credits`) counts that spend as well. Use a separate account or key for the assistant when a benchmark must have a known budget.

## Tinker

`/tinker MODEL` fine-tunes a model of your choice on your own sessions, for example `/tinker Qwen/Qwen3-30B-A3B-Instruct-2507`. Think saves the sessions of the current directory as traces (the exact history, system prompt and tools the model saw), trains a LoRA adapter on every assistant turn with [Tinker](https://thinkingmachines.ai/tinker/) in the background, and switches the chat to the new checkpoint when it is ready. Each later `/tinker MODEL` trains only on sessions that grew since the last round and resumes from the last training state, so the model keeps improving as you work. `/tinker` shows progress; `/model` switches back.

Think serves `tinker://` checkpoints through Tinker's OpenAI-compatible endpoint, so they work with every tool. The base model needs a tool-calling format (Qwen3, DeepSeek, Kimi, gpt-oss). Training needs `TINKER_API_KEY` and a Python with `tinker` and `tinker-cookbook` (`pip install tinker tinker-cookbook`); set `THINK_TINKER_PYTHON` if it is not `python3`. State, traces and logs are in `~/.local/state/inkling/tinker/`.
